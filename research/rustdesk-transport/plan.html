Wiring a RustDesk transport into T3 Code

You asked for two approaches — a Cordis-style plugin system with the RustDesk protocol as a plugin, or a direct modification. Here is the architecture analysis, the seam that already exists in the codebase, and a recommendation with a phased plan.

The verdict

Short version first. The full reasoning is in the sections below.

Recommendation

Do not build a Cordis-style plugin runtime. Build a narrow, house-style transport provider registry — the same shape as the repo's existing secret-provider-* registry — and make RustDesk the second implementation beside Cloudflare Tunnel.

  • The seam already exists. ManagedEndpointProvider already abstracts tunnel provisioning behind injectable tunnel/DNS clients, and RelayManagedEndpointProviderKind already reserves a "t3_relay" slot.
  • The real abstraction gap is the connector (cloudflared spawn + pin + update), not the provider — and that gap is what RustDesk actually forces you to confront.
  • A generic plugin runtime is a second, competing abstraction in a codebase that already has Effect Context.Service + Layer as its extension model. Two extension systems is a maintenance sink, not a feature.
But first — three things need fixing
  1. 1The "3 connections" is 3 linked machines, and it lives in T3 Code's own database. Swapping the transport does not touch it — it is a one-line constant.
  2. 2The free RustDesk servers have no accounts and no authenticator. TOTP is a paid Pro feature of a different service. Clerk already gives you MFA.
  3. 3T3 Code has no remote-control capability to plug RustDesk into. "Computer use" is a Codex tool label, not a T3 Code feature.

The honest framing of the goal

There are two separate problems hiding inside "use RustDesk's free servers because T3 Code limits 3 connections":

  • Problem A — link more than 3 machines. This is not a transport problem. It is a product/policy constant in T3 Code's relay. Fixing it takes one line, regardless of transport.
  • Problem B — stop depending on Cloudflare Tunnel. This is a transport problem, and it is a legitimate reason to want a RustDesk-style rendezvous + relay.

The plan below treats them separately, because a transport swap that does not move the cap would look like failure when it was actually a success.

Three premise corrections

Each of these changes what you would build, so they come before any architecture.

01
The limit

It is 3 machines, not 3 connections — and it is not a transport limit

Assumed"T3 Code limits me to 3 concurrent connections; a free relay with no cap will fix that."
Each T3 Connect account can link up to 3 machines. Phones and browsers do not count. A paid T3 Chat plan raises the limit to 10 machines with Pro, or 100 with Premier. — docs/user/remote-access.md

What it actually is: DEFAULT_MANAGED_TUNNEL_LIMIT = 3 at packages/contracts/src/relay.ts:969 — the number of linked environments (host machines) a Clerk account may hold a provisioned managed tunnel for. It is enforced in T3 Code's own Postgres, in infra/relay/src/environments/ManagedTunnelLimits.ts:173, serialised per user with a pg_advisory_xact_lock (line 159) and counted from the relayManagedEndpointAllocations table (lines 73–99).

Consequence: the count is a row count, not a transport property. A RustDesk transport that provisions a "managed endpoint" is still one allocation per machine, so the cap still applies — and a RustDesk transport that provisions no managed endpoint would fall outside the counter entirely, which is precisely the kind of accident you should not build on. Meanwhile the number of simultaneous clients (phones, browsers) connected to one machine was never capped.

Cheapest correct fix: raise the constant (one line) or insert a row into the relayManagedTunnelLimits override table — no transport work required. T3CHAT_PLAN_TUNNEL_LIMITS = { pro: 10, premier: 100 } (packages/contracts/src/relay.ts:972) already shows the intended knob.

02
Auth

The free RustDesk servers have no accounts — and no authenticator

Assumed"RustDesk has no limitations and there's authenticator support, so I get unlimited connections plus 2FA for free."
The empty default intentionally disables relay key validation… An empty key allows clients without a matching key to use the relay — rustdesk-server/docs/environment-variables.md:64

The split: RustDesk Server OSS (hbbs + hbbr) is a peer registry and a byte relay. It has no user table, no login, no OAuth, no TOTP — its own docs say "If you need a web console, API access, OIDC, LDAP, 2FA, device management… compare it with RustDesk Server Pro".

Where TOTP actually lives: rustdesk/src/auth_2fa.rs in the client — a totp_rs implementation for a RustDesk account backed by api.rustdesk.com. That is the paid account service, a completely different system from the public rendezvous/relay servers. The public servers you want to use inherit none of it.

Consequence: the public servers authenticate peers only by a shared symmetric licence key (src/relay_server.rs:466, src/rendezvous_server.rs:766) — a single public string. There is no per-user identity, no second factor, no revocation, no audit. T3 Code's Clerk-based identity, DPoP-bound tokens and per-environment scope checks are strictly stronger and would have to be re-implemented on top of the RustDesk transport rather than inherited from it.

What Clerk already gives you: Clerk supports TOTP / authenticator-app MFA and passkeys today. T3 Code has no 2FA of its own, so "add authenticator support" is a Clerk configuration task, not a RustDesk benefit.

03
Remote ctrl

There is no remote-control feature in T3 Code for RustDesk to fit into

Assumed"RustDesk's remote control fits T3 Code's computer use very well."
export const COMPUTER_USE_TOOL_SOURCE = { key: "computer-use", name: "Computer Use", kind: "computer" }; — packages/shared/src/toolActivity.ts:31

What "computer use" is today: a presentation label for a tool that the Codex provider executes. T3 Code renders the icon and title; it does not capture a screen or inject input.

What T3 Code actually implements: SnapShot (a one-way screenshot attached to a draft — no input, no remote transport); the Device panel, which drives iOS/Android simulators and emulators over a frame stream (packages/client-runtime/src/device/stream.ts); and a browser preview over a CDP relay. There is no "take over this machine from my phone" path.

Consequence: RustDesk's remote control (screen capture + uinput/CGEvent/SendInput injection) is a new feature, not an integration. And it rides on a completely separate stack from the transport: it needs RustDesk's video codec and input message formats, which are a far bigger lift than the relay work. The good news is that T3 Code's device layer already has the right shape — a frame sink in, a control channel out — so a RustDesk-style remote-control agent could drop in there without touching the agent/tool layer.

The two systems are shaped differently

This mismatch — a URL-shaped transport versus a peer-shaped transport — is the single biggest engineering fact in this plan, and it is invisible until you draw the paths.

Today — T3 Code gives the client a public URL

The client receives httpBaseUrl / wsBaseUrl and opens them directly. Everything downstream of the URL is interchangeable.

RustDesk — there is no URL; there are two peers

Both peers dial the rendezvous server, the server hands out a relay address, and the two peers are paired on the relay by a shared UUID. After pairing the relay is a pure byte pipe — src/relay_server.rs:461-498 pairs, 500-560 forwards raw bytes.

The consequence that decides the whole design

T3 Code's client runtime builds URLs from httpBaseUrl / wsBaseUrl (packages/client-runtime/src/authorization/service.ts:271-330) and speaks plain HTTP + WebSocket to them. A RustDesk transport produces no such URL. So a RustDesk transport is not a drop-in replacement for the tunnel — it requires a client-side transport agent as well as a host-side one, or the client runtime has to learn to speak the transport natively.

That agent needs somewhere to run. On desktop and mobile that is fine — a sidecar process exposing http://127.0.0.1:<ephemeral> to the existing client runtime, so zero changes are needed in the web/mobile/desktop apps. In a browser there is no sidecar, and RustDesk's WebSocket ports (21118 / 21119) would have to be spoken natively in the page — NaCl crypto in WebCrypto is a real project of its own.

Proposed seam — one registry, two implementations

The registry is a list of definitions, not a dynamic runtime — the same shape as secret-provider-definitions. Nothing is loaded at runtime, nothing is sandboxed, and the compiler still checks every implementation against one schema.

The three options

You named two; I am adding the third because it is what the codebase already implies.

A · Cordis-style plugin runtime B · Direct modification C · Transport provider registry recommended
Shape Generic plugin runtime: lifecycle hooks, dependency injection, hot-load, discovery, capability negotiation. RustDesk registered as one plugin among many. Add RustDesk branches inline to the existing Cloudflare-specific code paths. One TransportProvider interface plus a definition registry listing implementations. Effect-native, statically typed.
Touches A new cross-cutting runtime: new package, new lifecycle contract, new docs, new conventions, plus the RustDesk transport itself. Two extension systems coexist with Effect's Context.Service/Layer. The provider, the host runtime, the shared relay client, the client runtime, and the contracts — all Cloudflare-shaped. One new contract package, one registry package, one provider implementation, and the connector lifecycle extracted from the Cloudflare path.
Getting RustDesk in Same cost as C, plus the runtime. Plugin authoring becomes the product. Cheapest start, but every future transport repeats the work and the Cloudflare branches multiply. One interface to implement; the second transport afterwards is a file, not a framework.
Risk Highest. A generic runtime in a 741 MB monorepo with 9.7k forks is a fork-wide architectural change upstream will not merge. It also becomes a permanent maintenance obligation. Medium. Contained, but the Cloudflare assumptions stay tangled through the client runtime. Low. Bounded, reviewable, upstreamable, and idiomatic for this codebase.
Upstreamable? unlikely as a patch yes

Why not A, concretely

A Cordis-style runtime is not wrong in the abstract — it is wrong here, for three specific reasons:

  • The codebase already has an extension system, and it is Effect's. docs/internals/effect-services.md documents Context.Service + Layer as the house pattern, and the secret-provider-* packages are a worked example of "pluggable thing, registry style" that the team already accepted. A second runtime would compete with both.
  • The thing that needs to be pluggable is already pluggable. ManagedEndpointProvider already has its two I/O clients injected. Option A rebuilds a seam that exists, and does not fix the one that does not.
  • The seam that is actually missing is the connector, and no plugin runtime fixes it. cloudflared is spawned in ManagedEndpointRuntime.ts and pinned/downloaded/swapped in packages/shared/src/relayClient.ts (~700 lines). RustDesk needs a different connector binary with a different lifecycle. That is a connector registry problem: { id, version, urls, sha256, minVersion, install(), spawn(args) }.

If you still want a broad plugin system, it deserves its own proposal, its own branch and its own review — but it is not a prerequisite for shipping RustDesk, and bundling them makes both reviews harder.

The condition that would flip this to Option A

If the intent is to let third parties outside this repo ship transports as drop-in packages — a Cordis-like marketplace with runtime discovery — then A becomes correct and C is a stepping stone. Worth deciding explicitly, because it changes who has to live with the abstraction. T3 Code's existing secret-provider-* design suggests the team already answered this question in the negative: definitions are compiled in, not discovered at runtime.

Phased plan

Phases 0 and 1 are worth doing regardless of whether the RustDesk transport ever ships.

  1. Phase 0 · Spike3–5 days

    Prove the protocol, then choose the server

    Complete the RustDesk handshake end to end outside the product: the Ed25519-signed X25519 key exchange the server initiates on connect (rustdesk/src/common.rs:2306-2373), the NaCl crypto_box reply (create_symmetric_key_msg, common.rs:2449-2456), peer registration, punch-hole, and relay pairing by UUID. My probe already reaches the signed key-exchange against the live public server — the remaining steps are the crypto.

    Then decide, in this order: (1) public community servers vs self-hosted rustdesk-server OSS; (2) reuse hbb_common (AGPL) vs a clean-room implementation; (3) which side of the licence boundary the connector lives on.

    • poc/probe.py
    • research/protocol-notes.md
  2. Phase 1 · Unblock the cap1 day

    Lift the machine limit, independently of transport

    Make the machine cap configurable and raise the default: read it from configuration with a fallback, and keep the relayManagedTunnelLimits override row path for per-user exceptions. Update docs/user/remote-access.md and the error string in packages/client-runtime/src/relay/errorPresentation.ts:69-72 so the copy matches the real number.

    This alone answers "I am limited to 3" for anyone who only needed more machines — and it is the single highest-value hour in this whole plan. Do it before touching transport, so the RustDesk work is measured against the real remaining gap.

    • packages/contracts/src/relay.ts:969
    • packages/client-runtime/src/relay/errorPresentation.ts:69
    • docs/user/remote-access.md
  3. Phase 2 · Extract the seam4–6 days

    Introduce the transport contract and the connector registry

    Add the contract and the registry, then move Cloudflare behind them without changing behaviour. This phase ships value on its own: it is the piece that makes the next transport cheap, and it is a clean upstream PR on its own merits.

    • packages/contracts/src/transport.ts
    • packages/transport-core/src/
    • packages/transport-definitions/src/registry.ts
    • infra/relay/src/environments/ManagedEndpointProvider.ts
    • apps/server/src/cloud/ManagedEndpointRuntime.ts:729
    • packages/shared/src/relayClient.ts
  4. Phase 3 · RustDesk transport3–4 weeks

    Build the connector pair and the provider

    Write the connector as a separate AGPL-licensed binary in its own repository (e.g. dadahsueh/t3-rustdesk-connector), launched by the host exactly the way cloudflared is today — pinned, checksummed, self-updating. That keeps the AGPL boundary at the process edge instead of inside an MIT repo. Two roles in one binary: host role (register, accept sessions, proxy bytes to 127.0.0.1:port) and client role (request a session, expose a local origin for the existing client runtime).

    Then add RustDeskProvider to the registry. Note it provisions no Cloudflare tunnel and no DNS record — it returns a rendezvous descriptor plus a connector token — so the ManagedEndpointProvider bookkeeping still works, but the allocation semantics must be revisited against the 3-machine cap.

    • RustDeskProvider
    • connector: rendezvous client + key exchange + relay pairing + byte proxy
    • infra/relay/src/environments/ManagedEndpointProvider.ts
  5. Phase 4 · Client runtime1–2 weeks

    Teach the client runtime to use a non-URL origin

    Introduce a transport-session abstraction so the client runtime can talk to either a public HTTPS origin or a local sidecar origin. Desktop and mobile then need no app changes at all — the sidecar just appears as another route. The browser is the hard case: either keep the Cloudflare path for web only, or implement RustDesk-over-WebSocket (ports 21118/21119) natively in the page, which needs NaCl in the browser.

    • packages/client-runtime/src/authorization/service.ts:271
    • packages/client-runtime/src/transport/session.ts
  6. Phase 5 · Separate project4–8 weeks

    Remote control — a different project entirely

    RustDesk's remote control (screen capture plus input injection) is a product, not a transport. It needs RustDesk's video codec and input message formats, and it lands in the device layer (packages/client-runtime/src/device/stream.ts) where a frame sink and a control channel already exist. Attempting it inside the transport work will sink both. Sequence it after Phase 4, and treat it as its own design document.

Licence and policy

The one hard constraint on this design.

What the licences are

  • rustdesk/rustdesk-server — AGPL-3.0 (confirmed via gh api repos/…/license)
  • rustdesk/rustdesk (client) — AGPL-3.0
  • rustdesk/hbb_common — the shared protocol crate; no LICENSE file and no license field in its Cargo.toml, and it is vendored into rustdesk-server as a submodule at libs/hbb_common
  • pingdotgg/t3code — MIT

AGPL's copyleft reaches the whole work when you convey it. Linking hbb_common into the T3 Code server or client would put the MIT codebase at risk.

How to stay clean

  • Put the RustDesk client in its own repository, AGPL-licensed, as a separate process.
  • Let T3 Code download and launch it, exactly as it already does for cloudflared (packages/shared/src/relayClient.ts).
  • Communicate over a socket at arm's length. This is the same structure the Cloudflare connector already uses, so it is a familiar shape for reviewers.
  • Do not copy rendezvous.proto into the MIT repo — keep protocol knowledge in the AGPL repo or reimplement from observed behaviour.

This is a legal judgement, not an engineering one. Get counsel before shipping; the containment structure above is the standard mitigation, not a guarantee.

Using the free public servers for a third-party product

RustDesk's public community servers are a donation-funded service. Two separate issues, and the second is the one that bites:

  • Technically it works. The relay is a content-agnostic byte forwarder and the rendezvous protocol is fully specified, so a third-party client can register, be assigned a relay and tunnel bytes. My probe confirms a non-RustDesk client is accepted at the protocol level — it reaches the live public server's signed key-exchange. The servers apply rate limiting, bandwidth throttling and blocking, so a real product would be sharing a free resource with the entire RustDesk user base.
  • Policy-wise I did not find an explicit published statement permitting or forbidding third-party use of the public servers, and I would not build on that ambiguity. Ask RustDesk directly, or self-host.

Recommendation: self-host rustdesk-server OSS (AGPL, roughly the price of a small VPS) for anything real. Use the public servers only for local development and the Phase 0 spike. Self-hosting also gives you your own key pair, your own relay list, and no shared rate limits.

Decisions I need from you

These change the plan materially, so they are worth answering before Phase 2 starts.

  1. Is the goal more machines, or no Cloudflare? If it is only more machines, stop after Phase 1 — that is the whole fix. If it is Cloudflare independence, Phase 0 onward applies.
  2. Self-hosted RustDesk server, or the free public ones? Self-hosting costs a few euros a month and removes the licence-adjacent and policy ambiguity. Public servers are free and shared.
  3. Web client in scope? Desktop and mobile are straightforward with a sidecar. A browser needs RustDesk-over-WebSocket natively, which is a substantial sub-project. Keeping the Cloudflare path for web only is a legitimate option.
  4. AGPL boundary: separate AGPL repo for the connector (recommended), or a clean-room reimplementation inside a permissive licence?
  5. Is this for your own use, or to upstream? Upstreamability argues for the narrow registry (Option C). Personal use lets you go more direct.
