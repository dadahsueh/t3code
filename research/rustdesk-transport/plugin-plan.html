The plan in one screen

Your three decisions are mutually reinforcing — and one of them turns out to be forced by the AGPL boundary rather than optional.

Shape

Extract the pattern the codebase already uses three times, name it once, and apply it to the one axis that has none.

  • packages/plugin-core — a generic PluginDefinition + makePluginDefinitionRegistry + a cross-axis PluginCatalog, plus a PLUGIN_CONTRACT_VERSION the loader will check.
  • Each existing axis keeps its own strongly-typed definition that extends the generic one, so nothing is renamed and no package layout churns.
  • Transport becomes the first axis to use the spine properly — Cloudflare Tunnel, Tailscale and Manual become built-in plugins, and isAddon: true stops being a boolean nobody acts on.
  • RustDesk lands as plugin #1, and because it must live outside an MIT repo, it is also the first out-of-tree plugin — which is exactly why the runtime-ready contract is not optional.
The constraint that decides Phase 5
  1. 1RustDesk's server and client are AGPL-3.0. Your fork is MIT.
  2. 2So the RustDesk implementation cannot live in this repo — unless you relicense your whole fork.
  3. 3Compile-time-only plugins force everything into the repo. Out-of-tree loading is what keeps the licence boundary clean.
  4. 4Therefore: design the contract for out-of-tree from day one, ship compile-time wiring in v1, and build the loader in Phase 5.

What this replaces

You said "more machines" — and you are right that Tailscale already solves that: a link created with managedTunnelsEnabled: false deprovisions the managed endpoint and creates no allocation (infra/relay/src/environments/EnvironmentLinker.ts:292-312), so it never touches the 3-machine counter. That cap is DEFAULT_MANAGED_TUNNEL_LIMIT = 3 in packages/contracts/src/relay.ts:969 and it counts managed tunnels, not connections. No RustDesk work is needed to lift it — but if you want managed tunnels for more than three machines, raising that one constant still applies.

So RustDesk's remaining value is different from what you assumed: it is a reachability transport that needs no Cloudflare account, no DNS zone and no per-tunnel cost — which is a plugin-system requirement, not a machine-count one.

What the other axes agree on

Three independent axes converged on the same four-part shape without a shared package:

  • Definition — pure data plus pure functions. No I/O, no services. This is what makes it serialisable, which is what makes runtime loading possible later.
  • Driver / adapter — the behaviour, expressed as an Effect service or a set of operations. Separate from the definition so the definition can be shipped to a client that only renders a picker.
  • Registry — a lookup by kind, built from a frozen array. makeSecretProviderDefinitionRegistry and makeSourceControlDefinitionRegistry are near-identical, including the duplicate-kind guard.
  • Definitions package — the aggregate that names every built-in, with ordering rules where order matters (claimChangeRequestUrlsFirst, recognizeRemotesIn).

That is the spine to extract. It is not a Cordis clone — it is the pattern this codebase already chose, three times, independently.

The generic core

Small on purpose. AGENTS.md is explicit: do not introduce machinery because it looks architecturally impressive; fight for the smallest model that makes the correct behaviour unsurprising.

The contract — packages/plugin-core

Nothing is renamed and no package layout churns. The axis-specific definition keeps its own shape; it simply gains axis, a namespaced kind, and a config schema it already had.

Definition — the data half

// packages/plugin-core/src/shared/definition.ts
export const PluginAxis = Schema.Literals([
  "transport", "secret", "source-control", "provider",
]);

export interface PluginDefinition<Config = unknown> {
  /** Namespaced and stable: "transport/rustdesk". Never reused. */
  readonly kind: string;
  readonly axis: PluginAxis;
  readonly label: string;
  readonly description?: string;
  readonly configSchema: Schema.Codec<Config, unknown>;
}

Pure data, pure functions, no services — so a definition can cross the wire to a client that only renders a picker, and so it can be validated from a file on disk.

Registry — the lookup half

export function makePluginDefinitionRegistry<D extends PluginDefinition>(
  definitions: ReadonlyArray<D>,
  options?: { readonly order?: ReadonlyArray<string> },
): PluginDefinitionRegistry<D> {
  const byKind = new Map<string, D>();
  for (const d of definitions) {
    if (byKind.has(d.kind))
      throw new Error(`Plugin '${d.kind}' is defined more than once.`);
    byKind.set(d.kind, d);
  }
  return { definitions, find: (k) => byKind.get(k) };
}

This is makeSecretProviderDefinitionRegistry generalised — same duplicate guard, plus an ordering escape hatch borrowed from makeSourceControlDefinitionRegistry, whose claimChangeRequestUrlsFirst and recognizeRemotesIn options are exactly the "order matters" case.

One contract change you cannot skip

AdvertisedEndpointProviderKind and RelayManagedEndpointProviderKind are closed Schema.Literals. A plugin whose kind is only known at runtime cannot be expressed by a closed union. Both must become open, namespaced strings ("transport/rustdesk"), with the closed union kept only for the built-ins that the client needs to reason about specially.

Per AGENTS.md — "Anything crossing the wire is typed in packages/contracts. Change the schema and the server, web, mobile, and desktop all follow" — this touches every surface, and it needs the round trip: a way in, a way out, and a way to see it.

The transport axis

Transport is the axis that needs the plugin model most, because it is the only one with two different failure modes: host-side discovery and relay-side provisioning.

From hard-coded lists to one plugin interface

The interface has two optional operations because the two modes are genuinely different: advertise runs on the host and lists what is reachable right now; provision runs on the relay and creates an account-bound managed endpoint. Cloudflare needs the second, Tailscale needs the first, RustDesk needs both — and needs a client-side agent because it produces no public URL.

The capability flags that carry the weight

export interface TransportPluginDefinition
  extends PluginDefinition<TransportConfig> {
  readonly reachability: AdvertisedEndpointReachability;
  /** Whether this transport yields a URL a browser can open directly. */
  readonly providesPublicUrl: boolean;
  /** Whether a host-side binary must be present for it to work. */
  readonly requiresHostConnector: boolean;
  /** Whether a client-side agent must be present. */
  readonly requiresClientAgent: boolean;
}

These three booleans are the whole reason the transport axis could not be a plugin before: the client and the relay need to know, before choosing a route, whether the endpoint is a URL they can open or an agent they must attach to. Naming them in the contract is what lets the UI branch honestly instead of guessing.

RustDesk as plugin #1

It validates the contract harder than any built-in could, because it is the first transport that breaks the URL assumption.

What it proves

  • A plugin with no public URL. RustDesk yields peers, not addresses, so providesPublicUrl: false has to mean something real in the client runtime.
  • A plugin with two connectors. Host side and client side have to be pinned, verified and spawned independently.
  • A plugin outside the repo. AGPL forbids it living in an MIT monorepo, so the contract has to work across a process and a package boundary.
  • A plugin with real crypto. Ed25519 verification, X25519 key agreement, NaCl crypto_box, and a relay framing the plugin does not own.
  • A plugin that is not ours. The public servers are somebody else's infrastructure, so failure modes and rate limits are not yours to absorb.

What it costs

  • The client-side agent. RustDesk has no URL for the client to open, so either the client runtime speaks the transport natively, or a sidecar exposes a local origin. Sidecar is far cheaper — zero app changes on desktop and mobile — but it does not work in a browser.
  • The browser gap. A hosted web client cannot run a sidecar. Either web keeps the Cloudflare path, or the page speaks RustDesk over WebSocket (ports 21118 / 21119) with NaCl in the browser.
  • Licence containment. The implementation lives in a separate AGPL repository and is loaded as an out-of-tree plugin. The loader must be able to run a plugin it did not build.
  • Someone else's server. The public community servers are a shared free resource. Self-hosting rustdesk-server OSS is a small VPS and removes the ambiguity.

The licence constraint, stated plainly

rustdesk/rustdesk-server, rustdesk/rustdesk and rustdesk/hbb_common are AGPL-3.0 — and hbb_common has no licence file of its own, only its place inside the AGPL server tree. Your fork is MIT.

If the RustDesk implementation lived inside this repo, you would be distributing an AGPL work inside an MIT work. It cannot. So the RustDesk plugin must be out-of-tree: its own repository, AGPL-licensed, loaded at runtime by the plugin host.

This is why "both from day one" was the right call, and it is a stronger reason than extensibility for itself. Compile-time-only plugins and an AGPL RustDesk implementation are mutually exclusive. A separate process communicating over a socket is the standard "separate programs" arrangement, but this is a legal judgement — get counsel before you ship.

Runtime readiness, without a runtime loader

v1 ships compile-time wiring. The contract is shaped so that Phase 5 is additive, not a rewrite. The design rule that makes this work: the definition carries the data, the driver carries the behaviour, and the two are joined by kind.

One contract, two acquisition paths

Because the registry type is identical on both paths, adding the loader later is additive. The compile-time path stays the default, the safe path, and the one the settings UI shows by default.

What "runtime-ready" actually requires of the contract — four rules

  1. Definitions are data, and they validate. A definition read from disk must pass the same schema as a compiled-in one, or the plugin host is just a way to bypass the type system.
  2. Kinds are namespaced and never reused. "transport/rustdesk" — so a kind can be matched, routed and persisted without a closed union, and without two plugins colliding.
  3. A contract version exists and is checked. PLUGIN_CONTRACT_VERSION in plugin-core; a bundle declares the version it was built against and is refused on mismatch. Without this, a plugin compiled against an older contract fails somewhere deep in a call site instead of at load.
  4. Behaviour is behind a service, not in the definition. The definition is what a client renders; the driver is what the server runs. Splitting them is what lets the server refuse to load a plugin while still showing it in a picker.

Phases

Six phases. Phases 1 and 2 are worth shipping even if RustDesk never lands — they are the plugin system, which is what you actually asked for.

Risks, and the guardrails

Scope

"One generic core across all axes" is a real risk of becoming four half-migrated axes. The mitigation is ordering:

  • Phase 2 migrates one axis completely, end to end, before Phase 4 touches another.
  • Phase 4 is conforming, not rewriting — the axis keeps its own types and its own registry options.
  • If Phase 4 stalls, you still have a working plugin system on transport, which was the actual goal.

This ordering is the direct reading of AGENTS.md: "Do not preserve complexity just because it already exists… fight for the smallest model."

Security

Runtime plugins are code you did not write, running near credentials you care about. Three rules:

  • Out of process, always. A child process per plugin with a narrow IPC surface — the same shape as the cloudflared connector already in the tree.
  • Signed and version-checked. Manifest carries the contract version and a signature; a mismatch is refused at load, not at first call.
  • Explicit consent. Installing a plugin is a deliberate act, shown with its axis, its capabilities and what it can reach.

Licence

The one thing that cannot be engineered around.

  • RustDesk's implementation is AGPL-3.0 and lives outside this repo.
  • hbb_common has no licence of its own; do not vendor it.
  • A separate process over a socket is the standard separate-programs arrangement, but confirm with counsel before shipping.
  • Self-host rustdesk-server OSS for anything real — it is a small VPS and removes the shared-resource question.

Surfaces

Per AGENTS.md, a contract change lands on every client.

  • Open, namespaced kinds ripple through web, mobile and desktop.
  • Providers, contracts, the settings UI and the command palette each need a decision.
  • A plugin that adds a route must also add the way to remove it, and the way to see it.
  • Budget a round of "hit every surface" review — it is the most common defect class in this repo.

What I would do next

  1. Phase 1 now, on this branch. packages/plugin-core is additive, imports nothing, and can land on its own. It also settles the contract before anything depends on it.
  2. Phase 2 next, on this branch. Converting Cloudflare, Tailscale and Manual into plugins proves the model on a real axis without a licence question or a new dependency. When that lands, you have a plugin system — which was the actual ask.
  3. Phase 3 in a second repository. The RustDesk connector and bundle, AGPL, out of tree. This is where the licence boundary and the loader design get proven.
  4. Phase 5 before Phase 3 ships. The loader is what makes an out-of-tree plugin possible, so it cannot be scheduled after the thing that depends on it — even though it is written later.

Two things worth deciding before Phase 1: whether the plugin kind stays namespaced ("transport/rustdesk") or becomes a flat string with an axis field — namespaced is safer and costs nothing now; and whether a plugin may ship settings UI in v1, which I would defer, since a config schema plus a JSON form covers the first three transports without it.
